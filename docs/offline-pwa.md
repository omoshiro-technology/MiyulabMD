# PWA・オフライン閲覧仕様

## 1. 位置づけ

本書は PWA とオフライン閲覧の実装仕様である。実装済みであることを示すものではない。全体アーキテクチャは [設計書](design.md) を参照する。

選択肢・採用理由・見直し・検証とチェックポイントは [意思決定台帳](offline-pwa-decisions.md) に記録する。

**マイドライブ全体を対象にバックグラウンドで先読みし、端末にキャッシュが残っている範囲でフォルダ探索・ノート閲覧を可能にする。完全保存は保証しない。**

ローカルデータはサーバーデータの閲覧用キャッシュであり、バックアップ、オフライン編集用の作業コピー、サーバーと常に一致する複製ではない。失われてもサーバーのデータに影響せず、オンラインで再取得できるものとして扱う。

検討した「マイドライブ全体の保存完了を管理する方式」「閲覧したものだけキャッシュする方式」は採用しない。対象は全体、取得・保持はベストエフォートとする。

## 2. ゴールと対象外

### ゴール

- 初回オンライン起動で必要なアプリ資産をキャッシュした後、オフラインでもアプリを起動できる。
- キャッシュされたフォルダ構造・ノート一覧から、子フォルダ、親フォルダ、パンくずを使って探索できる。
- キャッシュされたノートを読み取り専用で閲覧できる。
- アプリ内遷移、直接 URL アクセス、再読み込み、アプリ終了後の再起動で同じ閲覧画面を使える。
- 通常の操作を妨げず、マイドライブ全体の先読みを順次試みる。
- 先読み中の通信断・タブ終了・容量不足で、既に有効なキャッシュを壊さない。
- キャッシュがない状態、古い状態、存在しないデータ、空のフォルダを区別する。

### 対象外

- オフラインでのノート新規作成、本文以外の更新操作のキュー。資格ありノートの本文オフライン編集と Yjs のオフライン永続化は、分離された編集キャッシュとして `specs/offline-mode.html` §4.3 / ADR 0001 に基づき実装済み（Issue #123）。
- 全件保存の保証、保存完了の証明、ダウンロード管理画面、永続的な取得キュー。
- アプリ終了後の継続ダウンロード、ブラウザや OS によるバックグラウンド停止の回避。
- 他人から共有されたドライブ全体の自動先読み。
- 外部画像、動画、iframe などの完全なオフライン表示。
- ノート履歴、設定画面、管理機能などのオフライン対応。
- ブラウザによるデータ整理や利用者による削除後のキャッシュ保持保証。

## 3. 保存対象と責務

### 3.1 対象範囲

自動先読みの対象は、自分のマイドライブ配下の全フォルダ、ノート、ノートが参照するアプリ内添付画像とする。公開範囲ではなく、マイドライブへの所属を基準にする。

通常の閲覧で取得したフォルダ・ノートも、閲覧ユーザーの区分でキャッシュできる。共有ノートを開くことは、共有ドライブ全体の先読み開始を意味しない。匿名閲覧のキャッシュはログインユーザーの領域と分離する。

マイドライブから外れたことを完全な一覧で確認した項目は、自動先読みの対象から外し、マイドライブの一覧キャッシュに残さない。本文等の回収は現在の参照を確認して行い、他の有効なキャッシュが使う画像を削除しない。

### 3.2 保存先

| 保存先 | 責務 |
| --- | --- |
| IndexedDB | ユーザー区分、フォルダ構造、パンくず、ノート一覧、本文・画像ファイルへの参照、更新情報、取得日時 |
| OPFS | ノート本文、アプリ内添付画像 |
| Cache Storage | アプリ起動用の HTML・JS・CSS・アイコン等 |

IndexedDB、OPFS、Cache Storage は通常同じオリジンのストレージ割り当てを共有する。OPFS 併用は独立した容量枠を増やすためではない。

ブラウザの HTTP キャッシュだけに依存せず、アプリが参照できるキャッシュを管理する。認証トークンや Cookie の値を閲覧キャッシュへ複製しない。

### 3.3 必要な管理情報

- ユーザー区分とキャッシュ形式のバージョン。
- フォルダ ID、親子関係、パンくず、一覧の取得範囲と完全性。
- ノートの正規 ID、取得に使った短縮 ID・別名等との対応。
- 一覧が示すサーバー更新情報と、保存した本文自身の更新情報。
- 本文・画像のファイル参照、取得日時、必要に応じた最終利用日時。

一覧の更新だけで本文を最新扱いにしない。本文未取得と空文字の本文、取得済みの空フォルダと未取得フォルダを区別する。

IndexedDB のフォルダキーは `JSON.stringify([userId, folderId])` とし、ユーザーと ID の構造を保った文字列で管理する。`null` を `"root"` 等の通常の文字列へ置き換えず、文字列 ID と衝突させない。OPFS のパス要素に使うエンコードとは責務を分ける。

## 4. PWA 起動基盤

- Web App Manifest にアプリ名、起動 URL、scope、表示モード、アイコンを定義する。
- Service Worker を登録し、オフライン起動に必要なビルド成果物を事前キャッシュする。
- フォルダ／ノート表示に必要な遅延ロード資産もオフラインで利用できるようにする。
- オンライン／オフラインで URL、React の画面、Markdown の表示処理を共通化する。
- オンラインでは既存のノートページのサーバー側プレビュー生成を維持する。
- オフラインの対応画面へのナビゲーションには、ノート本文を含まない共通の起動用 HTML を返す。データは IndexedDB／OPFS から読む。
- ユーザー固有の本文や初期データを埋め込んだ HTML を、共通の起動用キャッシュに保存しない。
- 認証、API、MCP、WebSocket の経路を起動用 HTML のフォールバック対象にしない。更新リクエストをキャッシュ・再送しない。
- アプリ資産はビルド単位で整合性を保つ。実行中の画面に強制再読み込みをかけず、新版適用と旧キャッシュ整理のタイミングを制御する。
- アプリ管理下の名前を持つキャッシュだけを更新・削除する。

既存の起動時 Service Worker 撤去処理と、撤去用の `public/sw.js` は置き換えてよい。複雑な公開運用向け互換機構は設けないが、テスト端末の旧登録からの更新は検証する。

HTTPS またはブラウザが安全なコンテキストとして扱う開発環境で動作させる。OPFS 等が利用できない場合はオンライン閲覧を維持し、オフライン用データキャッシュが利用できない旨を表示する。初期実装では別の本文保存方式へ黙って切り替えない。

## 5. データ読み出しと再検証

データ読み出しの入口を共通化し、画面ごとに通信・キャッシュ判定を重複実装しない。`navigator.onLine` は補助情報とし、実際の通信結果も使う。

| 状態 | 動作 |
| --- | --- |
| オンライン取得成功 | 取得結果を表示し、キャッシュ更新を試みる |
| キャッシュあり・再検証中 | キャッシュ由来と分かる形で先に表示できる |
| 通信不能・キャッシュあり | キャッシュを読み取り専用で表示する |
| 通信不能・キャッシュなし | オンラインで開く必要があることを表示する |
| 一時的なサーバー障害 | 最新確認に失敗したことを示し、既存キャッシュを利用できる |
| 明示的な権限拒否・削除 | 古いキャッシュへ無条件にフォールバックせず、対象を表示から除外する |
| キャッシュ破損・ファイル欠落 | キャッシュミスとして扱い、オンラインなら再取得する |

認証切れと個別項目の権限拒否は区別する。HTTP 401 やログインページへのリダイレクトを、単なる通信失敗や正常なデータ取得として保存しない。セッション切れ時の保持方針は第 9 節に従う。

再検証した本文を反映する際は、通常のオンライン編集中の内容を閲覧用キャッシュで上書きしない。

## 6. バックグラウンド prefetch

### 6.1 優先順位

1. 利用者が現在開こうとしているフォルダ・ノート。
2. マイドライブのフォルダ構造・ノート一覧。
3. 表示中のフォルダ内のノート本文。
4. その他の未キャッシュ・更新されたノート本文。
5. アプリ内添付画像。

少数の並列取得に制限し、通常の画面表示を優先する。通常取得と prefetch の同一項目への重複リクエストをまとめ、複数タブで全体の先読みが重ならないよう調整する。

### 6.2 起動・更新契機

- 起動・ログイン時。
- 通信復帰時。
- アプリが前面に戻った時。
- アプリ内のノート／フォルダ変更後。
- アプリ表示中の定期確認。

短時間の連続実行を抑制する。前面復帰と通信復帰などが重なっても、重複した全件確認を開始しない。再試行回数、定期確認間隔、並列数は実装時に定数として定義し、本番相当の負荷を見て調整する。

### 6.3 中断と再開

永続的なダウンロードキューや「何件目まで終わったか」というチェックポイントは保存しない。取得契機ごとに一覧とキャッシュを照合して候補を組み立て直す。

| 項目の状態 | 判定 |
| --- | --- |
| 有効なキャッシュなし | 取得候補 |
| 本文の保存版が一覧の更新情報より古い | 更新候補 |
| キャッシュがあり変更なし | スキップ |

取得中のアプリ終了や通信断では、その時点までに確定したキャッシュを残す。同じ項目を再取得しても壊れない処理にする。バックグラウンド実行が停止されることを正常な中断として扱う。

### 6.4 失敗と停止

- 単発の取得失敗は他の項目を妨げず、限定的に間隔を空けて再試行する。
- 通信の連続失敗、認証切れ、容量不足では先読みを停止する。
- 次の取得契機で再評価できるが、短時間の停止・再試行ループを作らない。
- 容量不足を検知した後は、保存できないデータを取り続けない。
- 個別の閲覧要求はバックグラウンド停止中でもオンライン取得できる。

## 7. 保存の整合性と更新

### 7.1 IndexedDB と OPFS の更新順序

両者をまたぐ単一トランザクションは使えないため、既存ファイルを直接上書きしない。

1. OPFS の新しいファイルに本文または画像を書き、書き込みを完了する。
2. IndexedDB のトランザクションで、そのファイルへの参照と対応する更新情報を確定する。
3. 参照されなくなった旧ファイルを、後から安全に回収する。

途中終了時は、旧版か新版の完全なデータを参照する。本文更新の失敗を理由に旧版を先に削除しない。IndexedDB の確定に失敗した新ファイルは未参照ファイルとして回収する。

未参照ファイルの整理は、書き込み中のファイルや他タブが利用中のファイルを誤って削除しないよう調整する。起動時や読み出し時にファイル欠落が分かった場合も、アプリ全体を起動不能にしない。

ノートと閲覧ユーザー情報の書き込みでは、小さな共通処理がトランザクションの完了・失敗・中止とリスナー解除を所有する。同期例外や、トランザクション作成直後の中止も後片付けの対象にする。OPFS の書き込みストリームは取得後の全経路を後片付けの範囲に含め、最初の書き込み前に中止された場合も `abort()` する。既に確定したデータを後片付けで削除せず、元の中止理由・失敗を維持する。

コミットと中止が競合した場合、保存の成否は IndexedDB の実際の確定結果で判断する。`complete` になった保存を、遅れて届いた中止や `abort()` の失敗だけで保存失敗へ変えない。参照済み本文を「未参照」と仮定して削除しない。読み取りセッションの破棄による結果返却・画面反映の中止は、確定済みデータの保持とは別に判断する。

### 7.2 一覧の完全性

途中まで取得した一覧を完全な一覧として扱わない。ページングがある場合は全ページの成功を確認する。

新しい一覧の取得完了までは前回の有効な一覧を残す。取得途中の失敗や部分的な結果を根拠に、載っていないフォルダ・ノートを削除しない。完全な一覧との照合後に、構造・所属・先読み対象を更新する。

一覧に存在しないことだけでサーバーから削除されたと断定しない。所属変更と閲覧権限の喪失を区別する。

### 7.3 本文と画像

本文と画像の利用可否を別に管理する。画像が未取得でも本文を表示できる。複数ノートが参照する画像の回収では、有効な参照が残っていないことを確認する。

OG カードは取得済み情報があれば利用し、なければ通常リンクへ縮退できる。外部コンテンツの取得失敗で本文表示を失敗させない。

### 7.4 サーバー更新情報

キャッシュの取得日時と、サーバー本文の更新情報を混同しない。サーバー側で確定した閲覧用本文を取得対象とし、未送信の編集内容を閲覧キャッシュへ保存しただけで「サーバー保存済み」と扱わない。

現在の一覧・本文 API が返す更新情報と、共同編集から閲覧用スナップショットへの反映タイミングを実装前に確認する。既存の更新情報だけで本文の変化を安全に判別できない場合は、リビジョン等の識別情報を補う。

## 8. 容量不足とキャッシュ保持

- 永続ストレージを要求できる環境では `navigator.storage.persist()` を利用する。拒否されてもオンライン機能を継続し、保持を保証しない。
- `navigator.storage.estimate()` は概算として利用する。空き容量の見積もりだけに頼らず、実際の書き込み失敗を処理する。
- 容量不足では未参照ファイル等を安全に整理する。解消しなければ、その回の prefetch を打ち切る。
- オンラインで取得した内容は、キャッシュ書き込みに失敗しても表示できる。
- 書き込みに失敗した内容を「キャッシュあり」と表示しない。旧版が残る場合はその取得日時を維持する。
- 初期実装では、有効なキャッシュを容量不足のたびに自動削除して先読みし直す仕組みを設けない。期限・容量上限・LRU の具体的な導入は別途判断する。
- ブラウザや利用者によるキャッシュ削除は通常のキャッシュミスとして扱う。
- 詳細な容量管理画面、本文のみ保存モード、容量不足時の整理ウィザードは作らない。

設定に「端末キャッシュを削除」を設ける。確認後に閲覧用キャッシュを削除し、サーバーデータは変更しない。操作中は取得処理を止め、その回の自動 prefetch は再開しない。後続の通常閲覧や次回起動では再びキャッシュできる。アプリ起動用資産はこの操作の削除対象外とする。

## 9. 認証・権限・ユーザー切替

| 状態 | 方針 |
| --- | --- |
| 通信できず認証確認不能 | 前回ユーザーのキャッシュを読み取り専用で利用する |
| オンラインでセッション切れを確認 | prefetch を停止し、保存済み閲覧を維持して再ログインを案内する |
| 明示的なログアウト | そのユーザーの本文・一覧・画像・メモリキャッシュを削除する |
| 別アカウントへ切替 | 前のユーザーの表示・取得を停止し、キャッシュを削除して切り替える |
| 個別の権限拒否・削除を確認 | 対象を表示から除外し、関連キャッシュを安全に回収する |

ローカルのユーザー識別情報は閲覧キャッシュを選ぶための情報であり、有効な認証やサーバー権限の証明には使わない。古い編集権限を使って更新操作を許可しない。

ログアウト・切替・キャッシュ削除では取得を中止するだけでなく、遅れて返るレスポンスの表示・保存を拒否する。複数タブにもユーザー変更を伝え、メモリ上の本文を含めて前ユーザーの情報を残さない。

オフライン中の権限変更を即時に反映・回収することはできない。また、端末やブラウザプロファイルを利用できる人は、保存済みの非公開ノートを閲覧できる。自動キャッシュの説明にこの制約と削除方法を記載する。

### 9.1 閲覧状態・失敗分類・更新可否の共通化

画面ごとに個別のオフライン判定を足す方式ではなく、サーバー認証済みの状態と、前回ユーザーのキャッシュを閲覧する状態を共通の状態管理で明確に分離する。

- 通信失敗、HTTP エラー、JSON 解析・データ処理のエラーを共通の取得層で区別する。取得から表示までを一括で `catch` し、すべてを通信不能として扱わない。レスポンス本文の転送中断も通信失敗として区別できるようにする。
- 意図的な取得の中止と、想定外の例外は元のまま伝え、通信エラーに変換しない。`AbortSignal` の独自の中止理由も維持する。中止を契機とするキャッシュへのフォールバックや再試行を行わない。
- 取得と本文読み取りを一つの共通リクエスト処理が所有し、有効な中止情報を最後まで保持する。`RequestInit.signal` の省略・`undefined` は入力 `Request` の signal を引き継ぎ、明示的な `null` はそれを解除する。
- 非成功の HTTP 応答はステータスを一律に保持し、特定のコードだけを例外扱いしない。エラー本文を取得・解析できなければ `statusText` を使い、独立した通信エラーへ変換しない。レート制限、サーバー障害、権限拒否を区別した上で、上位の読込処理が再試行やキャッシュ表示を判断する。意図的な中止や想定外の例外は、このフォールバックで隠さない。
- キャッシュ閲覧では既存のプレビューを再利用し、編集用の操作経路を表示から切り離す。同じ URL とアプリの枠組みを維持する。
- UI の表示制御だけに頼らず、更新処理の入口でも共通の許可判定を行う。フォルダ変更、共有設定、履歴復元、タスク更新、共同編集を含め、個別ガードの付け忘れに依存しない。
- 前回ユーザーの復元情報と、そのユーザーの本文キャッシュの保存順序・整合性を保証する。独立した fire-and-forget 処理の完了順に依存させない。

### 9.2 読み取りセッションと結果の所有権

- ノート取得はユーザーごとの読み取りセッションが所有する。ユーザー情報を開始時に固定し、呼び出し元のオブジェクト変更や別セッションの開始によって、取得済み・取得中のデータの所属を変えない。
- 取得完了時のグローバルな「現在のユーザー」を保存先に使わない。中止・破棄された処理は、新しいセッションの表示やキャッシュへ結果を流さない。
- 本文、閲覧ユーザー、実際の取得元、キャッシュ取得日時を一つの読み取り結果として返す。UI と更新ガードは同じ結果を参照し、別々の Map や認証状態だけから取得元を推測しない。
- ネットワーク・キャッシュ・HTTP 失敗の結果は共通の返却経路へ集め、全非同期処理の後、返却直前にセッションの有効性を確認する。その確認と返却の間に新たな非同期処理を挟まない。既に完了した Promise を後から中止へ変えることはせず、結果受領後の画面反映では呼び出し側も現在のセッションとの対応を確認する。
- 認証 API が成功していても、ノートをキャッシュから表示する場合は読み取り専用とする。
- 結果の `cachedAt` は表示に使ったキャッシュの実際の取得日時とし、ネットワーク応答を表示する場合は `null` とする。表示時刻や説明文で実際の日時を代用しない。
- 403・404 を確認した場合は、該当するメモリ／永続キャッシュを無効化し、その後の通信不能で古い本文を復活させない。取得失敗・中止時も進行中リクエストの管理を片付ける。

### 9.3 閲覧禁止の記録と物理削除

- 閲覧を禁止する論理状態と、本文ファイル・一覧レコードの物理削除を分ける。ユーザーとノートを特定した禁止記録を先に永続化し、物理削除に失敗しても、本文と一覧はその記録に従って対象を返さない。
- 物理削除は再試行できる処理とする。削除失敗を理由に禁止を解除せず、無関係なノートや別ユーザーのキャッシュを削除しない。読み取りセッションを作り直した場合も、保存済みの禁止を維持する。
- 禁止記録そのものを保存できない場合は、そのユーザーの稼働中のキャッシュ利用を停止する。新しいキャッシュハンドルにも適用し、単に I/O が再び成功しただけでは再開しない。HTTP の拒否結果を維持した上で、`cacheWarning` に手動クリアが必要な旨を返す。
- 拒否処理の入口は DB 接続の成功に依存させない。DB を開けない場合も禁止記録の保存失敗として扱い、同じユーザーの既存・新規ハンドルと読み取りセッションへ利用停止を適用する。通常のキャッシュミスとして処理を省略せず、別ユーザーのキャッシュ利用は維持する。
- ストレージがすべての変更を拒否する場合、再起動を跨ぐ禁止状態の永続化は保証できない。その状態を無効化完了と表示せず、利用停止・手動クリアの案内を行う。
- ユーザー・ノートごとに拒否前後の要求を区別する。拒否より前に開始した要求は、遅れて成功しても表示・再保存・禁止解除に使わない。拒否後に新しく開始した要求がサーバーから成功応答を得た場合に限り、正常な保存とともにノート単位の禁止を解除できる。判定はセッション作成時ではなく各要求の開始時を基準とし、前述のユーザー単位の利用停止を自動解除するものではない。
- ユーザー単位の停止は本文・フォルダ・一覧のすべてのキャッシュ操作に適用する。停止前に開始した別ノートの読み取り、保存、禁止解除も対象とし、開始時だけの判定に依存しない。未完了の処理を停止し、返却直前にも利用可否を確認する。ただし既に確定したトランザクションを後から未確定扱いにしたり、参照中の本文ファイルを削除したりしない。正常なネットワーク応答によるオンライン閲覧は、キャッシュ利用停止とは切り分けて維持する。

## 10. 閲覧 UI

### フォルダ

- 既存のフォルダビューを使い、キャッシュされた子フォルダ、ノート一覧、パンくずを表示する。
- 子フォルダ名だけ取得済みでも、その内部までキャッシュされているとは限らない。
- ノート一覧に名前があっても本文を表示できるとは限らない。
- 未取得フォルダに「このフォルダは空です」と表示しない。

### ノート

- オフラインではプレビューによる読み取り専用表示を基本とする。本人所有・書き込み範囲「自分のみ」・編集ロックなし・オンライン同期済みのノートだけ、表示キャッシュ由来でも編集キャッシュ（y-indexeddb のローカル Y.Doc）を復元して本文のオフライン編集を許可する。編集は端末に保持され、再接続・認証後の同期でマージされる。資格のあるノートはオンライン閲覧中に共同編集セッションを先行接続し、同期済み Y.Doc を編集キャッシュへ永続化するため、編集モードに入ったことがなくてもオフラインで本文編集に入れる。
- オフライン状態はヘッダーのオフラインアイコン（ロゴ右）で示し、ホバー・タップで最終同期時刻をポップアップ表示する。
- キャッシュなしの場合は、オンラインで開く必要があることを表示する。
- 古い本文を表示できる場合は更新失敗によって消さず、古いキャッシュであることを示す。
- 画像がない場合は本文を維持し、該当箇所で未取得または利用不能を示す。
- キャッシュファイルが空の本文でも、未取得扱いにしない。

### 更新操作

オフライン時は作成、削除、名前変更、移動、共有・公開設定変更、画像アップロード、履歴復元を無効にする。本文中のタスクチェックボックスも更新させない。資格のある本人ノートに限り本文の編集モードへの切替を許可する（上記「ノート」参照）。それ以外のノートは編集モードへの切替も無効とする。

UI と更新処理の入口の両方で制御する。閲覧のみのノートでは共同編集接続を開始しないが、オフライン編集資格のあるノートでは編集キャッシュの温め・復元のためオンライン閲覧中から Yjs セッションを開始し、WebSocket 接続は再同期のために試行を続ける。オンライン編集中に通信が切れた場合は、資格の有無にかかわらずサーバー再同期まで新たな本文編集を許可しない。切断前に入力済みの内容を破棄・上書きしないことを前提に、既存の共同編集ライフサイクルとの接続を実装時に検証する。

### 表示の最小化

「全体保存完了」「全件ダウンロード進捗」は表示しない。オフライン表示の説明、取得日時、キャッシュなしの案内、設定内の削除操作を基本とする。背景の単発取得失敗を繰り返し通知せず、必要ならキャッシュ利用不能・書き込み失敗を控えめに案内する。

## 11. 実装前の確認事項

以下は合意済みの機能範囲を変更するものではなく、実装で解決すべき技術確認である。

- マイドライブの一覧 API の範囲、ページング、完全性の判定。
- ノート本文の変更識別と、共同編集から閲覧 API への反映タイミング。
- ノートの正規 ID、短縮 ID、別名の解決と無効化。
- 添付画像の参照抽出、取得権限、変更識別、重複参照の扱い。
- 対応ブラウザでの OPFS、IndexedDB、Service Worker の動作。
- 複数タブの取得主体、キャンセル、ユーザー変更通知、ファイル回収の調停。
- アプリ更新時の IndexedDB スキーマと OPFS ファイル形式の移行。閲覧キャッシュが移行できない場合も、オンライン機能を起動不能にしない。
- prefetch の並列数、確認間隔、再試行回数、容量不足後の再評価間隔。

## 12. 実装順

1. Service Worker 撤去処理を置き換え、Manifest、アイコン、起動用資産、ナビゲーションのフォールバックを整備する。
2. IndexedDB／OPFS のキャッシュ層と、ユーザー分離・安全な更新・削除を実装する。
3. 共通の取得層をフォルダ／ノートビューに接続し、オフライン閲覧・未取得表示を実装する。
4. 読み取り専用制御、認証切れ、権限拒否、ユーザー切替を接続する。
5. マイドライブ全体のベストエフォート prefetch と画像キャッシュを実装する。
6. 中断・容量不足・複数タブ・アプリ更新を含む検証を行う。

## 13. 受け入れ条件と検証

### 基本ワークフロー

- オンラインで起動して資産と一部データを取得後、通信を切ってアプリを閉じる。オフライン再起動で取得済みフォルダを探索し、ノートを閲覧できる。
- `/`、`/f/:folderId`、`/n/:id`、`/s/:id` を直接開く・再読み込みする場合も、対応するキャッシュがあれば表示できる。
- 未キャッシュのフォルダ・本文は適切な案内となり、空のデータや 404 と混同しない。
- 本文が空のノート、画像未取得、外部埋め込み未取得でも画面が壊れない。
- オフライン閲覧操作から更新 API の送信や新規の共同編集接続が発生しない。

### prefetch と中断

- 利用者が開いていないマイドライブ内のノートも、先読み成功後はオフラインで開ける。
- 通常の閲覧要求を優先し、同じ項目の通常取得と先読みが重複しない。
- 先読み中に通信断・タブ終了しても確定済みキャッシュが使える。
- 次回起動で候補を再構築し、有効で変更のないキャッシュをスキップできる。
- 再開前にサーバー側で追加・更新・移動・削除しても追従できる。
- 一覧取得を途中で失敗させても、既存項目が誤って削除されない。

### 保存・容量

- OPFS 書き込み中、書き込み完了後、IndexedDB 確定前後で中断し、旧版または新版の完全な本文を参照できる。
- 容量不足を注入すると先読みが停止し、オンライン閲覧と既存キャッシュが維持される。
- 保存失敗後の無限再試行、大量の無駄なダウンロード、未参照ファイルの無制限な蓄積がない。
- 本文・画像のファイル欠落やキャッシュ全消失を起こしても、キャッシュミスとして復帰できる。
- キャッシュ削除操作でサーバーのデータが変化せず、進行中レスポンスが削除直後にキャッシュを復元しない。

### 認証・更新

- オフライン認証確認不能とセッション切れでは保存済み閲覧を維持する。
- 個別の権限拒否・削除確認後は対象キャッシュを表示しない。
- ログアウト・別アカウントへの切替を取得中かつ複数タブで実施し、前ユーザーのデータが表示・再保存されない。
- 旧 Service Worker 登録から新版へ更新でき、資産更新で旧 JS と新 HTML の不整合や強制的な作業破棄が起きない。

### 検証環境

公開運用前のため、本番環境へ直接デプロイして検証できる。Web ビルド成果物を Worker から配信し、本番のノートページ生成経路を通す。Vite 開発サーバーでの確認だけで完了としない。

ユニットテストでは候補選定、失敗分類、更新情報の比較、完全な一覧による照合を検証する。ストレージの結合テストでは中断・容量不足・参照整合性を検証する。ブラウザでは実際のオフライン再起動、OPFS、Service Worker 更新、認証・複数タブの動作を確認する。
