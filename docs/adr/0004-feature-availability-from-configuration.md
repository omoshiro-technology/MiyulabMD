# 0004. サーバー側の機能可用性は「設定の実在」由来にする

- ステータス: 採択
- 日付: 2026-09-16（設計合意時点。実装前）
- 関連: `specs/knowledge-management.html` §2.4 / §2.7

## コンテキスト

ナレッジ管理機能を opt-in 化するにあたり、「機能が使えるか」をサーバー側で
どう判定するかが問題になる。素朴な実装では `settings.knowledge.*` フラグを
API / MCP のゲートにするが、これはフラグと実データの二重管理を生む
（「フラグ ON だがスペースなし」「スペースがあるがフラグ OFF」）。

## 決定

サーバー側は**機能フラグでゲートせず、設定データの実在で可用性を決める**。

- MCP のツール公開: `para_spaces` が 1 件以上あれば `para_*`、
  `medallion_sets` があれば `medallion_*`、スキーム設定フォルダがあれば
  `jd_*` / `scheme_*` をリストに出す。未設定ならツール自体が存在しない。
- REST API もフラグゲートを設けない。`GET /api/para` は未セットアップなら
  `{ spaces: [] }` を返すだけ（`ensureParaBuckets` 除去後は副作用ゼロ）。
  `POST /api/para/enable` はセットアップ手段なので常に呼べる。
- `settings.knowledge.*` は UI 表示の制御（PARA セクションやメニュー項目の
  表示/非表示）にのみ使い、サーバー動作・データ・MCP には影響しない。

## 検討した代替案

- フラグ OFF 時に API を 403 / MCP ツールを「未設定」エラーにする →
  二重管理と、「エラーを返すと AI が設定を試みる」余地を残すため不採用。
- フラグで MCP ツールリストをフィルタ → UI の好みとサーバー側の能力を
  混同するため不採用。

## 影響

- 「未 opt-in なら副作用ゼロ」は、`enable` を呼ばなければデータが生まれない
  ことで構造的に保証される（フラグではなく副作用の有無で制御）。
- UI の OFF は純粋に表示隠しであり、スペース・層セット・スキームの実データと
  MCP ツールは残る。再 ON で即復帰する。
- MCP ツール数はユーザーの設定状況で動的に変わる。ツール列挙時に
  設定実在の問い合わせが必要になる。
