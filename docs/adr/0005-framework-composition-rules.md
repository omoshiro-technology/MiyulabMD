# 0005. ナレッジ管理フレームワークの複合ルール

- ステータス: 採択
- 日付: 2026-09-16（設計合意時点。実装前）
- 関連: `specs/knowledge-management.html` §2.5 / §2.6、`CONTEXT.md`（フレームワークの複合ルール / スペース）

## コンテキスト

PARA スペース・メダリオン層・命名規則という複数のフォルダ属性フレームワークを
持つと、「同じフォルダに複数の属性を付けられるか」「属性同士を入れ子に
できるか」という複合の境界を決める必要がある。利用者の自由度を優先しつつ、
人間が構造を把握できなくなる状態だけは防ぎたい。

## 決定

- **異なるフレームワーク同士の併用・入れ子・同一フォルダ指定は全て許可**する。
  例: PARA バケツにメダリオン層を割当てる（Project 単位の層管理）、
  層フォルダ配下に命名規則フォルダを置く、スペース内にメダリオン構造を作る。
- **同一フレームワークのフラットな重複のみ禁止**する。1 フォルダが持てる
  同一フレームワークの役割は最大 1 つ（1 バケツ / 1 層割当 / 1 スキーム /
  スペースルート xor バケツ）。
- **同一フレームワークの入れ子は許可**する。スペース内に別スペース、
  層フォルダ内に別層割当を置け、**内側の割当が優先**する
  （メダリオンは「最も近い祖先の割当が勝つ」継承ルール）。
- スペースルートは自分のドライブ内の任意フォルダ（共有フォルダ内は不可）。
  ルートを持たない default スペースはオーナーごとに最大 1 つ。
  スペース名はオーナー内一意（DSL / plan API の名前解決のため）。

## 検討した代替案

- スペースルートをトップレベル限定・ネスト禁止 → Project 単位で PARA や
  層を回したい需要（例: プロジェクト内に独自の PARA 構造）を塞ぐため不採用。
- フレームワーク間の併用も制限 → 「Archives は output 層」のような自然な
  運用まで禁止になり、利用者の自由度を損なうため不採用。
- 同一フレームワークのフラット重複も許可 → 1 フォルダが複数バケツ・複数層を
  兼ねると表示・検索・人間の理解のすべてが曖昧になるため不採用。

## 影響

- フォルダ属性は `para_space_id`+`para_bucket`、`medallion_set_id`+
  `medallion_layer`、`scheme` の独立した列で表現され、互いを侵食しない。
- 同一フレームワークのフラット重複はスキーマの一意性・単一ペア列で構造的に
  防ぐ（アプリケーションチェックに依存しない）。
- 入れ子の結果として、外側スペースの PARA ツリー内に内側スペースが
  ネストして表示される。検索 DSL の `para:` / `layer:` は名前解決に
  スペース名・セット名を使う。
