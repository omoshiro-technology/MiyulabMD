1.3 問題点

問題 A PARA が「暗黙に always-on」かつ「暗黙にフォルダを採用」している。 GET /api/para は内部で ensureParaBuckets（apps/worker/src/services/para.ts:56-81）を呼び、 バケツ未割当なら同名の既存トップレベルフォルダを自動で「採用」（para_bucket を付与）、 無ければ新規作成する。つまり HomePage の fetchPara（pages/HomePage.tsx:435-448）が ログイン済みユーザーの初回表示で Projects / Areas / Resources / Archives を勝手に作る。 「Projects」という自分のフォルダが既にあると、それが警告なく PARA の Projects バケツに格上げされる。
問題 B フォルダ作成 API は冪等で競合エラーを返さない。 ensureFolderRow（apps/worker/src/services/access.ts:819-847）は同パス既存時に既存行を返すだけで、 POST /api/folders（routes/folders.ts:279-334）は 409 を返さない。 「名前がぶつかったら作成を止めて名前変更を促す」UX は現 API では表現できず、 事前に衝突を検出する専用の仕組みが必要。
問題 C 編集ヘッダーに機能が雑に詰め込まれている。 右 nav に最大 9 要素が一列。層・フォルダ・リンク・履歴は使用頻度が「共有」「モード切替」より低いのに 同じ視覚的重さで並び、狭い幅ではアイコンだけが連なって判別不能になる。 さらに opt-in 機能を今後増やすと、この行は確実に溢れる。
問題 D 設定に「アカウント横断の機能フラグ」という概念が無い。 現在の設定永続化は全て localStorage（lib/editor-tab.ts miyulabmd:editor-tab-key、 lib/theme.ts miyulabmd:theme、lib/editor-mode.ts miyulabmd:editor-mode）で、 端末ごとの UI 好みしか保存できない。サーバー側にユーザー設定ストアが存在しないため、 「PARA を有効化した」というアカウント状態を表す場所が無い。
問題 E PARA ツリーは 1 オーナー 1 本しか持てない。 folders.para_bucket は (owner_id, para_bucket) で一意に引かれる （apps/worker/src/services/para.ts:31-38）ため、「個人」と「仕事」で PARA を分けるような 複数ツリー運用を表現する場所がスキーマに存在しない。対応は §2.5「スペース」で行う。
問題 F メダリオン層がノート単位で、フォルダ管理と直交している。 現行の層は notes.layer（bronze 既定）+ gold_unlocked_until + note_layer_events の per-note モデル（apps/worker/src/db/schema.sql:27-28,148-153）。 その結果、1 つのフォルダ内に bronze/silver/gold が混在し、ツリー表示から「どこに何の品質のものがあるか」が読めない。 層は本来「精緻度のステージ」であり、整理の単位であるフォルダに割り当てるほうが構造と一致する（§2.6 で再設計）。

2.設計方針

2.1 opt-in 原則

  • 新しいナレッジ管理フレームワーク機能は全て opt-in（デフォルト OFF）とする。データを作る副作用（フォルダ自動生成など）は、ユーザーが明示的に有効化するまで一切起こさない。
  • wiki-link と検索 DSL は標準機能としてトグル対象外とする。wiki-link は常時 ON で困る副作用が無い。検索 DSL は演算子を「使わなければ結果に影響しない」性質のため、jd: / para: 等をユーザーが使っていなければ該当結果を返さないだけで、機能自体をゲートする意味がない。パーサ・補完・リンクパネル・演算子はコア機能として常に有効。
  • 既存の常時 ON 機能のうち 層 / 命名規則 は後方互換のためデフォルト ON のままとし、同じトグル UI から opt-out 可能にする。「機能を無効化してもデータは消えない・サーバー動作は変わらない」ことを UI に明記する（例: 層を OFF にしてもノートの編集ロックは残る — 層は表示ラベルのみでロックは別機能、§2.6）。
  • PARA はデフォルト OFF に転換する（現状の暗黙 auto-create を廃止）。既に para_bucket が付いたフォルダを持つユーザーは「有効」として移行する（後述の移行ルール）。
  • 有効化は機能ごとに独立したトグル。機能間の依存（例: PARA アーカイブはフォルダ移動に依存）は機能内部で解決し、トグル同士は連動させない。

2.3 opt-in 状態の保存先

選択肢を比較する。結論は B（サーバー保存）を唯一の権威とし、A をセッション内のちらつき抑制ミラー、 D を再訪問時の初回ペイント用ヒントとして併用。保持するクライアント側データは最小限にし、 設定画面は開いた時点で必ず最新のサーバー値を取り直す（ミラーに依存しない）。

  • ログアウト・アカウント切替・キャッシュ削除時は identity-lifecycle.ts のライフサイクルに乗せてミラーを消去する。
  • ミラーに入れるのは機能フラグの真偽値のみ（パス・タイトル等のコンテンツ情報は入れない）。
移行ルール デプロイ時、para_bucket が 1 つでも割当済みのユーザーは knowledge.para = true として初期化（現状維持）。 それ以外は false（新規挙動）。これにより既存ユーザーのドライブ構造は変わらず、 新規ユーザーには PARA フォルダが勝手に生えなくなる。

2.4 PARA 有効化フロー（競合検出 → 一時停止 → 名前変更 → 再実行）

ユーザーの要望どおり、「既存フォルダと名前がぶつかる場合は作成をいったん止め、被っているフォルダの名前変更を促すモーダル」を 状態機械として定義する。現行 ensureParaBuckets は衝突を「暗黙の採用」で解消するが、これを ユーザー承認制に改める。

無効化（OFF）の意味 OFF にしても para_bucket 割当とフォルダ自体は残す（削除しない）。効果は UI 側のみ: ① NoteTree の PARA セクション非表示（通常フォルダとして並ぶ）、 ② 「完了してアーカイブ（PARA）」メニュー非表示。 サーバー側は設定の実在を見るため GET /api/para は OFF でもスペースを返し、MCP の para_* ツールも残る（§2.7）。 再 ON で即座に復帰（再セットアップ不要、plan は全て assigned）。

2.5 複数 PARA 運用（スペース）

「個人」と「仕事」で別々の PARA ツリーを持ちたい需要に対応するため、PARA の実体を 「スペース」= ユーザー命名のルートフォルダ + 4 バケツのセットとして複数定義できるようにする。 例: トップレベルに「個人」「仕事」フォルダを作り、それぞれの配下に Projects / Areas / Resources / Archives を持つ。

現行モデルの制約

バケツ識別は folders.para_bucket 列で、検索条件は WHERE owner_id = ? AND para_bucket = ?（apps/worker/src/services/para.ts:31-38）。 つまり 1 オーナーにつき各バケツ 1 行 = PARA ツリーは 1 本しか持てない。 複数運用には「どのツリーのバケツか」の識別子が必須。

スペースの構造ルール

  • スペース名は同一オーナー内で一意（para_spaces(owner_id, name) に一意制約）。para:work.projects や plan?space= の名前解決を一意にするため。スペース名とルートフォルダ名は独立（adopt/rename してもスペース名は変わらない）。default スペース（ルートなし）は DSL では para:projects（全スペース横断）に含まれる。
  • スペースルートは自分のドライブ内の任意のフォルダでよい（共有フォルダ内のスペースは認めない。権限と表示の混乱を防ぐ）。ルートを持たない default スペースはオーナーごとに最大 1 つ。
  • 同一フレームワークのフラットな重複は禁止: 1 フォルダが持てる PARA の役割は最大 1 つ（スペースルート xor バケツ）。1 フォルダが 2 つのスペースのバケツを兼ねる、バケツフォルダが別スペースのルートになる、等は不可 — 人間が管理できなくなるため。
  • 入れ子は許可: スペースの配下に別スペースを置ける（例: 個人/Projects/myproj/ が別スペース「myproj」のルート）。内側のスペースは独立した PARA ツリーとして扱い、外側スペースのツリー表示ではネストして見せる。
  • バケツ名の衝突判定はスペースルート直下の子に限定する。「個人/Projects」と「仕事/Projects」は別物であり、互いに衝突しない。
  • スペースルートフォルダ自体の衝突（既存フォルダ「個人」がある等）は、バケツと同じ rename / adopt / skip の 3 択で解決する（§2.4 のモーダルを流用）。adopt した既存フォルダが中身を持っていてもよい。
  • スペースの削除 = スペース割当の解除。para_space_id / para_bucket を外すだけでフォルダは残す（OFF と同じ思想）。ルートフォルダごと消す場合は通常のフォルダ削除に任せる。
属性の複合ルール（全フレームワーク共通） 利用者の自由度を優先し、異なるフレームワーク（PARA / メダリオン層 / 命名規則）の併用・入れ子・同一フォルダ指定は全て許可する。 例: PARA のバケツフォルダにメダリオン層を割当てて Project 単位で層管理する、層フォルダ配下に命名規則フォルダを置く、スペース内にメダリオン構造を作る。 禁止するのは同一フレームワークのフラットな重複だけ（1 フォルダに 2 つのバケツ / 2 つの層割当 / 2 つのスキーム）。 同一フレームワークの入れ子（スペース内スペース、層フォルダ内の別層割当）は許可し、内側の割当が優先される。

2.6 メダリオン層のフォルダ割当化（再設計）

現行の per-note 層（notes.layer）をやめ、層をフォルダの属性にする。 ここでの層は「そのディレクトリに置く情報の種類」を表す表示ラベルであり、 昇格の仕組みは持たない。編集の可否は層とは独立した「ノート単位の編集ロック」で運用する。

層の構成は固定ではなく、PARA のスペースと同様にユーザーが複数の「メダリオン設定（層セット）」を定義できる。 1 つのセットは「名前 + 順序付きの層リスト」（例: セット「精緻度」= raw / knowledge / output、 別セット「成熟度」= draft / review / published）。フォルダには「どのセットの、どの層か」を割り当てる。

データモデル

要素構造備考
medallion_sets（新規テーブル） (id, owner_id, name, layers JSON /* 順序付き層リスト */, created_at) 1 オーナー複数セット。GET /api/medallion/sets で一覧、セットごとの層リストを取得できる
フォルダへの割当 folders.medallion_set_id + folders.medallion_layer（セット内の層キー） 割当はフォルダのコンテキストメニュー「層の割当…」から。名前と層は独立

既定セット「精緻度」（raw / knowledge / output）をプリセットとして用意し、シンプルに使いたいユーザーはそれだけで運用できる。 割当たフォルダとその配下のノートにはメダル相当のバッジが表示されるだけで、 層による編集・削除の制限は一切設けない。

knowledge silver raw を読んで作成した資料・メモ
output gold knowledge から作成したレポート・成果物

セットの編集規則

  • 層キーは immutable（raw 等の識別子）。編集できるのは表示ラベルと順序のみ。フォルダの medallion_layer はキー参照なのでラベル改名で割当が壊れない。
  • 層の追加は自由。削除は割当済みフォルダがある場合は不可（エラーを返し、先にフォルダの割当を外させる）。割当ゼロの層のみ削除可。
  • セットの削除は許可（確認ダイアログ付き）。削除すると配下のフォルダ割当は全て解除されるが、フォルダ自体は残す（PARA スペース削除と同じ思想）。

割当と継承のルール

  • 1 フォルダ = 最大 1 割当（medallion_set_id + medallion_layer の単一ペア）。同一フォルダに複数セットの層は付けられない（フラット重複の禁止、§2.5 の複合ルール参照）。
  • 最も近い祖先の割当が勝つ: 自分に割当があれば自分、なければ親を遡る。層フォルダ配下に別セット/別層の割当を置く入れ子は許可され、内側が優先される。
  • PARA バケツ・スペースルート・命名規則フォルダとの同一フォルダ併用・入れ子は全て許可（§2.5 複合ルール）。

表示

  • フォルダツリー: 層が割り当てられたフォルダにメダルバッジを表示（NoteTree の行アイコン脇）。子フォルダはパス継承で同じ層として扱う。
  • エディタヘッダー: ノートを開いているとき、所属フォルダの層に応じたメダルバッジを表示する（情報表示のみ、操作は持たない）。
  • フォルダ移動（FolderPopover / DnD）で別の層フォルダに入れれば、そのノートの表示層も変わる。「昇格」という操作・イベント・履歴（note_layer_events）は存在しない。

編集ロック（層と独立・ファイル単位）

  • ノートごとに 「編集ロック」フラグを持たせる（現行の per-note gold ロック機構を層から切り離して一般化したもの）。ロック中はあらゆる変更操作をサーバー側で拒否する: 本文編集（DocumentRoom 更新拒否）・削除・フォルダ移動・共有変更・改名すべてブロックし、UI にはバナーと「ロック解除」導線を出す。許可されるのは閲覧とロック解除のみ（変更したい場合は必ず解除が先）。
  • ロック/解除は UI のトグル操作。時間制の自動解除（gold_unlocked_until 相当）は廃止し、解除は常に明示操作とする。層フォルダの種類とは無関係にどのノートでも使える（「raw 配下の原本をロックする」は代表的な運用例に過ぎない）。
  • AI / MCP 経由の制御: unlock_gold_for_edit を set_edit_lock(id, locked) に置き換え、解除（locked: false）のみ confirm: true パラメータを必須にする（promote_note の gold 昇格と同じ既存慣例）。ロックは confirm 不要（安全側の操作なので）。実際の承認 UX は MCP クライアントのツール承認画面に委ね、サーバーは「confirm パラメータなしでは解除できない」一点を強制する。 「原本データを置いたら編集不可にする」等の振る舞いはプロンプトで指示する運用に委ねる。

なぜフォルダ割当 + 独立ロックが合うか

  • 構造と一致する: per-note 層は「フォルダ内に bronze/gold が混在する」状態を許し、ツリーから精緻度が読めなかった。フォルダ割当ならパスを見れば分かる。
  • 既存の仕組みに乗る: folders テーブルは既に scheme / para_bucket というフォルダ属性列を持つ。medallion_sets + フォルダの割当列の追加で済み、ロックは既存の per-note 機構をそのまま使う。昇格ゲート・層イベント・フォルダ制約の新設は全て不要になる。
  • 継承が自然: folders はパスベースなので、raw/ に割り当てれば raw/2026/ 等の子は prefix 判定で同じ層表示になる（scheme の採番スコープと同じ仕組み）。
  • スペース・PARA と直交して組み合わせられる: 個人/raw 仕事/output のようにスペース配下に層フォルダを置ける。PARA は「時間・行動軸」、層は「情報種別軸」で役割が被らない。

検索 DSL・MCP への波及

  • layer: 演算子をフォルダ割当層に再定義する。layer:output = 全セット横断で層キー output のフォルダ配下、layer:精緻度.output = セット指定（para: の para:work.projects と同じ構文規則）。
  • MCP の list_notes_by_layer は廃止し、search_notes の layer: 演算子で代替。medallion_* ツール（セット一覧・層割当）は機能トグルに連動。

移行

  • medallion_sets テーブル新設 + folders に medallion_set_id / medallion_layer を追加。既存フォルダは未割当（層なし）。既定セット「精緻度」（raw / knowledge / output）はユーザーが層機能を有効化した時点でシードする。
  • 既存の notes.layer は deprecated。ノートの振り分けウィザードは提供しない — per-note 層は実質未使用（管理対象ノートが存在しない）のため、振り分けの必要がない。層を使いたいユーザーはフォルダ割当を新たに行う。
  • gold ロック（gold_unlocked_until）は「編集ロック」フラグへ読み替えて継承。note_layer_events・昇格ゲート・層別一覧 API は撤去対象。
  • 層の無効化（OFF）はメダル表示の非表示のみ。編集ロックは別機能なので OFF にしてもロック中ノートのバナーと解除導線は残る。

2.7 機能レジストリによる拡張性

PARA 以外のフレームワーク追加（タグ軸管理、MOC、将来の独自スキームなど）に備え、 設定を「機能レジストリ」として定義する。各機能が自身のセットアップ手順を持つ構造。 

// apps/web/src/lib/knowledge-features.ts（新規・案）
type KnowledgeFeatureKey = "para" | "schemes" | "layers"; // wiki-link・検索DSL は標準機能のため対象外

type KnowledgeFeature = {
  key: KnowledgeFeatureKey;
  label: string;
  description: string;
  /** true = 新規ユーザーにデフォルト ON（後方互換の既存機能のみ） */
  defaultEnabled: boolean;
  /** 有効化に副作用がある場合のセットアップ（PARA のみ実装、他は undefined） */
  setup?: (ctx: SetupContext) => Promise<SetupOutcome>;
  /** この機能が UI に出すもの（ヘッダー/サイドへの差し込み宣言） */
  surfaces: { homeSection?: boolean; contextMenu?: boolean; editorHeader?: boolean };

  • UI 側は useKnowledgeFeature(key) フック（viewer.user.settings.knowledge を読む）で出し分け。NoteTree の paraBuckets prop、folderMenuItems の「命名規則…」「完了してアーカイブ（PARA）」「層の割当…」、ツリーとヘッダーのメダルバッジ表示などが対象（wiki-link の LinksPanel ボタンは標準機能のため対象外）。
  • MCP のツール公開は機能フラグではなく「設定の実在」で決まる: para_spaces が 1 件以上あれば para_* ツールが現れ、medallion_sets があれば medallion_*、スキーム設定フォルダがあれば jd_* / scheme_* が現れる。未設定ならツール自体がリストに存在しない（AI が「見つけて呼ぶ」経路が最初から無い）。settings.knowledge フラグは UI 表示の制御であり、サーバー側のゲートにはならない。
  • REST API も同様にフラグゲートを設けない。GET /api/para は未セットアップなら { spaces: [] } を返すだけ（ensureParaBuckets 除去後は副作用ゼロ）。POST /api/para/enable 自体がセットアップ手段なので常に呼べる。
  • 将来のフレームワーク（例: 「タグ軸管理」= タグ名の正規化・タグツリー表示）は setup を持たない単純トグル、または別の setup を持つ機能として 1 エントリ追加するだけで設定画面・ヘッダー差し込み・API ゲートが揃う。

3.3 opt-in 連動ルール

  • opt-in 機能が OFF のとき、その機能由来のヘッダー要素はレンダリングしない（disabled 表示もしない）。例: layers OFF → メダル表示が消えるが、ノート単位の編集ロックは別機能として残るため、ロック中ノートのバナーと解除導線は消さない（§2.6）。schemes OFF → 「命名規則…」メニュー項目が消える。wiki-link 由来の「リンク」ボタンは標準機能なので常に出る。
  • PARA 有効時のヘッダー変化は増やさない方向で設計する: エディタヘッダーには載せず、ホーム画面の PARA セクションとコンテキストメニューに留める。将来「ノートをバケツへ移動」等のショートカットを足す場合も「⋯」メニュー内項目として実装する。
  • メニュー内項目が全て OFF になった場合、「⋯」ボタン自体を描画しない。

リスクと留意点

  • 既存ユーザーの暗黙 PARA 化を止めると API 挙動が変わる: GET /api/para の副作用除去は後方互換を壊す（呼べば必ずバケツができる契約だった）。MCP 経由で para_list を暗黙セットアップとして使う利用者がいないか確認し、changelog / マイグレーションで補う。
  • 編集ロックと層 UI の分離: メダリオン層を OFF にしてもノート単位の編集ロックは残る（層は表示ラベルのみのため）。ロック中ノートのバナーと解除導線は層トグルに依存させない。
  • MCP 経由のロック解除: AI が解除できてしまうと「原本保全」が形骸化するため、解除は confirm: true パラメータ必須（サーバー側で強制可能な範囲）。承認 UX 自体は MCP クライアントのツール承認画面に依存し、クライアントが承認を求めない実装なら confirm 送信だけで通る点は限界として許容する（既存 promote_note と同水準）。
  • オフラインキャッシュとの整合: viewer・設定ミラー（sessionStorage / localStorage）は lib/offline-cache.ts / identity-lifecycle.ts のライフサイクルに乗せ、ログアウト・キャッシュ削除時にミラーを消す。localStorage ヒントは共用 PC で他ユーザーの値が残り得るため、値内の userId 照合で不一致を破棄する（§2.3）。
  • 共有フォルダ内の PARA メニュー: 「完了してアーカイブ（PARA）」は owner 自身のコンテキストでのみ意味を持つ。現行も canAdmin + Projects 配下判定で絞っている（home-page.ts:430-450）が、フラグ条件を追加する際にこの判定を壊さない。
  • 複数スペースの一意性移行: (owner_id, para_bucket) 一意から (owner_id, para_space_id, para_bucket) 一意への変更は、既存行を default スペースにバックフィルしてから制約を張る順序が必要。スペース導入後に「ルートに直接作成」を選んだ場合は default スペースのバケツ名と衝突し得る点に注意（plan がスペース単位で判定するのでモーダルで検出できる）。
