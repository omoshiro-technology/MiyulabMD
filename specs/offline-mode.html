MiyulabMD — Offline Mode Redesign

オフラインモードの再設計

現行のオフラインキャッシュは「正しさ」を保つために巨大な権威フェンス機構を抱えており、 その複雑さ自体が障害の温床になっている。本書はデータモデル（サーバー／IndexedDB／同期構造）の 整理、実コードから読み取れる問題点、目指す UX、そして 「表示キャッシュと編集キャッシュの完全分離」を軸にした再設計をまとめる。

対象: apps/web フロントエンド 主な参照: src/lib/offline-cache.ts (約 3,800 行) 関連仕様: docs/offline-pwa.md 直近の障害: PR #117「Offline cache scope invalidated」
要約（TL;DR）

現行設計は「キャッシュを fail-closed な権威として扱い、全トランザクションを epoch でフェンスする」 方式で、安全側に倒しすぎた結果、中断した purge が durable な :purging 墓標を残してキャッシュ全体を恒久的に塞ぐ、タブ間の suspend 通知が 解除されない、表示経路がキャッシュ権威の失敗で道連れになるという 問題を抱えている。推奨案は、「ネットワーク優先・キャッシュはフォールバック」 に倒し、durable に残す権威を「拒否台帳」と「purge 墓標（自己修復つき）」だけに限定する 方式への段階的移行である。さらにキャッシュを「表示キャッシュ」と 「編集キャッシュ」に完全分離し、編集はサーバーと同じ Yjs に任せる （ローカルは y-indexeddb、対象は「編集権限が自分だけ」のノートに限定）。 同期・マージの複雑さは Yjs に委譲し、自前の権威フェンスは表示キャッシュ側の 薄い拒否台帳だけに縮退できる。

1 回のキャッシュ操作で起きること

openOfflineCache でハンドルを開くと、全操作がロック＋前後 2 回のスコープ検証で ラップされる（offline-cache.ts:3744-3797）。

openOfflineCacheshared user lock ⊂ shared global lock → scope 捕捉readScopeEpochs → composeEpoch → assertScope（前）epoch/lifetime/suspend 検証 → 操作本体guardTransaction が書込txn内で再検証 → assertScope（後） → 呼び出し側の公開境界lifetime/generation/suspend 再確認
  • scope = {userId, epoch, lifetime}。epoch は composeEpoch(device-epoch, user-epoch) の base64 化した合成値 （offline-cache.ts:473-479）。
  • guardTransaction（offline-cache.ts:707-742）は全書き込み トランザクション内で 3 つのメタデータキーを再読込し、epoch 不一致・:purging・ device-clear-state ≠ active・suspend・lifetime 不一致なら transaction.abort() する。IDB の直列化を利用したフェンス。
  • invalidateRealm / invalidateDeviceRealm（offline-cache.ts:400-423）は lifetime を進め、進行中操作を abort し、開いているハンドルを close する。 BroadcastChannel で他タブにも伝搬する。
  • 拒否系は個別の順序機構を持つ：ノートはインメモリ世代（note-access-order.ts） ＋ durable な note-order シーケンス、フォルダは durable な folder-denial-sequence、画像は resource-order:image:* カウンタ。

2現状の問題点

実コードから読み取れる問題を、障害への影響度順に列挙する。多くは「正しさを守るための機構」 そのものが新たな故障モードを生んでいる。

P0 中断した purge が durable な :purging 墓標を残し、キャッシュが永久に塞がれる

purgeOfflineCacheUser は削除トランザクション内で user-epoch:<user> に "<uuid>:purging" を書き込み（offline-cache.ts:1157）、 OPFS 削除の後、別トランザクションで <uuid> へ書き換える （offline-cache.ts:1461-1466）。この間にタブが死ぬと墓標が残り、 readScopeEpochs → isPurgingEpoch が永久に invalidatedError()（"Offline cache scope invalidated" AbortError）を 投げ続ける。復旧手段は手動の端末キャッシュ削除のみで、自己修復経路が存在しない。

端末全体削除も同型で、purgeOfflineCacheDevice は updateDeviceState(PURGING)（:1580）→ 削除 → updateDeviceState(ACTIVE, epoch)（:1588）の間に死ぬと device-clear-state="purging" が残り、全ユーザーの全キャッシュ操作が恒久的に失敗する。

影響: 直近の「フォルダ一覧が一切表示できない」障害の根本原因候補。PR #117 は表示側の緩和のみ。

P0 タブ間で suspend が解除されない（broadcast による伝搬毒）

globalSuspended を false に戻すコードは purge 実行タブ内の purgeOfflineCacheDevice だけ（offline-cache.ts:1589）。 device-invalidate の BroadcastChannel を受けた他タブは invalidateDeviceRealm() で globalSuspended = true になるが、 戻す経路がなく、ページリロードまで全キャッシュ操作が失敗する。 リロードしても durable な device-clear-state が残っていれば同じく塞がれる。

suspendedUsers も同様で、suspendedUsers.delete は purgeOfflineCacheUser の成功時のみ（:1471）。 拒否書き込みの失敗で suspendOfflineCacheUser が呼ばれると （note-read-session.ts:504-520 等）、generation=null の拒否イベントが broadcast され、受信した全タブでも同ユーザーが suspend される （handleDenialLifecycleMessage: offline-cache.ts:425-432）。 しかもインメモリなのでリロードすると fail-closed の保証自体が消える —— 片方では「解除不能」、 もう片方では「保証が消える」と、両方向に壊れている。

影響: 一時的な IndexedDB エラーが、全タブのキャッシュをセッション終了まで殺す。

P1 表示経路がキャッシュ権威に結合していて、権威の失敗が UI を殺す

readHomeMetadata はネットワーク取得成功後も assertOfflineCacheScope(scope)（home-metadata-reader.ts:397-399）と validateHomePublication（:237-258, 422-428）で scope を再検証し、 失敗すると AbortError が読み取り全体を潰す。さらに projectCachedHomeMetadata がネットワーク結果をキャッシュから読み戻して射影するため、 キャッシュ読み取りの失敗がオンライン表示に波及する。 HomePage 側は invalidationRetryRef による 1 回リトライで対症療法を入れている （HomePage.tsx:539-596）が、これは権威機構が生み出した例外へのバンドエイドである。 コメント "Cache availability must not gate healthy network display" （offline-cache.ts:589）と実際の挙動が矛盾している。

影響: 「ネットワークは正常なのにフォルダ一覧が出ない」という最悪の UX 障害。

P1 状態機械が複雑すぎる — 「世代」が 4 系統、検証が全 await 境界に分散

単一ファイルにこれだけの「世代」概念が同居している:

  • epoch 系: device-epoch × user-epoch の合成 scope epoch
  • lifetime 系: userLifetimes / clearLifetimes / globalLifetime（全てインメモリ）
  • durable 順序系: note-order / folder-denial-sequence / resource-order:image
  • インメモリ順序系: noteGenerations / nextGeneration / currentShortIds（note-access-order.ts）

全キャッシュメソッドが isUserSuspended / currentUserLifetime / currentNoteGeneration の検査を各 await の前後に手書きで繰り返す （例: getNote offline-cache.ts:3430-3490 は同じチェックを 6 回）。 biome-ignore noExcessiveCognitiveComplexity が 4 箇所（:3281, :3333, :3430, :3571）。 決定台帳 docs/offline-pwa-decisions.md の D45, D46, D49, D57, D58, D63, D72, D76, D119 は、いずれも「この境界のチェックが抜けていた」型の修正であり、 構造的に見落としが再発する設計であることを示している。

P2 fail-closed の保証がリロードで消える / セッション中は解除不能

suspendedUsers はインメモリのみ。拒否マーカーの永続化失敗による suspend （安全側の停止）は再起動すると存在しなかったことになり、仕様書 §9.3 の 「I/O が再び成功しただけでは再開しない」という意図と矛盾する。 逆にセッション中は purge 成功以外に解除経路がなく、一時エラーで死んだキャッシュは ユーザー操作なしに復帰しない。

P2 metadata ストアの雑多さと、purge 削除リストの手管理

clearUserRecords（offline-cache.ts:1156-1186）は削除対象キーを プレフィックス列挙で手書きしており、新しいマーカー種別の追加時にここを更新し忘れると ユーザーのキャッシュ消去が不完全になる。権威情報と参照情報が同居しているため 「何を消せば purge 完了か」が自明でない。

P2 purge が保留中の OPFS 書き込みを待つため、遅延・スタックの余地がある

pendingUserWrites を purge が Promise.all で待つ （offline-cache.ts:1454, 1582-1584）。タブを殺せば待ち自体は消えるが、 「purge がいつ終わるか分からない」状態をユーザー操作（ログアウト）の前に置く構造。

P3 モジュールロード時の副作用と二重 BroadcastChannel

void getEpochDatabase()（offline-cache.ts:194）が import 時に DB を開く。ライフサイクル系と identity 系で BroadcastChannel が 2 本 （miyulabmd-offline-cache-lifecycle / miyulabmd-identity-invalidation） あり、通知の責務が重複している。また currentShortIds の ID 束縛は タブ内のみで、他タブの束縛は durable マーカー経由でしか追えない。

問題の構造的理解

個々のフェンスは全て「前の障害を防ぐため」に追加された正当な機構である（決定台帳 R01–R04, D22, D125）。しかし結果として、安全性を守るはずの durable 権威自身が 最大の故障モードになった。fail-closed を「正しさ」ではなく 「障害時の UX」として評価し直す必要がある。

3目指す UX

「ファイルマネージャー（フォルダ階層・ノート一覧）」と「ノート本文」に分けて、 各シナリオでの理想的な振る舞いを定義する。大原則: キャッシュの内部状態が ユーザーの操作をブロックしない。キャッシュの失敗は常に「データがない」として表現し、 エラーで画面を殺さない。

3.1 ファイルマネージャー（/, /f/:id）

シナリオ理想的な振る舞い
オンライン ネットワーク応答をそのまま表示。キャッシュ保存は detach された best-effort で、保存失敗は控えめな警告のみ。表示をブロック・失敗させない。
オフライン キャッシュ済みのフォルダ階層とノート一覧を読み取り専用で表示。未取得フォルダは「オンラインで開いてください」と案内（空フォルダと区別）。キャッシュ権威の異常は「未キャッシュ」と同じ扱い。
再オンライン直後 現在の表示を維持したままバックグラウンドで再取得し、差分をその場で反映。readonly から編集可能へ昇格。リロード不要。
複数タブ 各タブが独立して読める。一方のタブでキャッシュ削除が起きても、他タブは「キャッシュが空になった」とみなして再取得または案内を表示。伝搬 suspend で殺さない。
アカウント切替 旧ユーザーのキャッシュは削除され、新ユーザーに旧データが一切表示されない。削除が中断しても次回起動時に完了する。
purge 中断後 次回オープン時に自動で purge を完了（またはやり直し）し、「空のキャッシュ」または正常キャッシュとして動作。永久に AbortError を出さない。

3.3 応答速度の要件 — 「オフライン機構が無かった時代」と同じ速さ

オンライン時の表示速度は、オフライン対応が存在しなかった頃（fetch → render のみ）と 同等を維持する。キャッシュの読み書きは表示のクリティカルパスに乗せないのが原則。

4新設計の提案

4.1 設計原則

  1. 表示キャッシュと編集キャッシュを完全分離する — 「見るためのコピー」（フォルダ・一覧・本文スナップショット・画像）と 「書くための複製」（Y.Doc）を別ストア・別契約で持つ。 表示側は読み捨て可能なキャッシュとして極限まで薄く、 編集側は Yjs の同期モデルに丸ごと委譲する。 両者が 1 つの権威機構を共有しない。
  2. キャッシュの失敗は UI を殺さない（fail-soft） — 読み取り失敗は「キャッシュミス」、書き込み失敗は「警告」のみ。キャッシュ内部由来の AbortError を UI へ露出しない。UI が見る中止は自分のナビゲーション abort だけ。
  3. durable に残す権威は 2 種類だけ — 「拒否台帳（denied-note / denied-folder / denied-image）」と「purge 墓標」。 前者は 403/404 の復活防止に必須の安全機構、後者は自己修復のために残す。
  4. インメモリ状態はタブをまたがない — BroadcastChannel は「ヒント」に格下げし、正は常に IDB。通知を逃したタブでも 読み取り時に正しい状態を観測する。通知を受けても「再読み込み」するだけで、 自分の状態を不可逆に変えない。
  5. 中断は常に自己修復できる — 墓標を見つけたら、ロックで生存確認して purge を完了/巻き取る。 「手動クリアまで復旧不能」という状態を設計から排除する。
  6. 表示経路は純粋な流れ — fetch → snapshot → display。保存と拒否台帳の射影は 分岐した detached / 到着時再射影の処理で、読み戻しのためにキャッシュを開き直さない。
  7. オンライン表示速度はキャッシュ導入前と同等 — クリティカルパスに IDB/OPFS の読み書きを直列で挟まない（§3.3）。 キャッシュ層のウォームアップと保存は表示と並列〜表示後に行う。

4.2 表示キャッシュ / 編集キャッシュの完全分離

再設計の中核は、§1.6 で見えた「二重の本文」を、役割の異なる 2 層に分離すること。 現行は 1 つのキャッシュ機構（IDB v4 + OPFS + epoch フェンス）が表示と編集の両方を抱え込んでいるが、 両者が求める性質は全く違う。

4.3 編集キャッシュ = Yjs + y-indexeddb

既に createYjsSession（lib/collaboration.ts:99-161）は y-websocket の WebsocketProvider で DocumentRoom DO と同期している。 ここに y-indexeddb の IndexeddbPersistence を足すだけで、 オフライン編集・変更の永続化・再接続時の自動マージが成立する。 同期プロトコル・CRDT マージ・awareness は全て既存の経路Bをそのまま使う。

EditorPage既存 Y.Doc "markdown" → IndexeddbPersistence編集のたびに IDB へ update 蓄積 ＋ WebsocketProviderオンライン時のみ接続 ⇄ DocumentRoom DOYjs sync で双方向マージ → D1 markdown_snapshot従来どおり射影
  • オフライン編集: provider が切れていても Y.Doc への編集はそのまま可能。 変更は update として y-indexeddb に積まれ、provider.synced で 「未送信の編集あり」を UI に表示できる。
  • 再接続: 接続回復で y-websocket の sync step が走り、 サーバー側 Y.Doc と自動マージ。マージアルゴリズムは Yjs の責務で、 自前コードは接続の on/off と資格判定だけ。
  • 編集ロック中のノートは除外: ロック中は閲覧のみ。 （注: ロック機構は現在 gold 層ベースだが、汎用の「編集ロック」に 分離される方向 — CONTEXT.md 参照。いずれにせよロック中は編集資格なし。） オフライン中に遠隔でロックされた場合、未送信 update はサーバーに 拒否され得るため「同期待ち」として残し、ロック解除後の sync に委ねる。
  • 「自分だけが編集可能」に限定する理由: CRDT は任意の同時編集をマージできるが、オフライン期間が長いほど サーバー側との乖離が大きくなり、他人の編集と大きくマージする局面は ユーザー体験上予測しにくい。effectiveWriteScope === "self" （packages/shared/src/permission.ts:181-219）であれば 実質的なライターは自分だけで、マージは「自分のオフライン分を 追記するだけ」に縮退し、衝突らしい衝突が起きない。
  • 資格の喪失: ノートが共有化・ロックされたら 「新たに編集可能にする」対象から外れるが、ローカル doc の削除は 同期済みと確認できてから。未送信 update を含む doc は絶対に 自動削除しない —「同期待ち」として残し、次回オンライン時に sync を試みる。 サーバーが拒否する場合（ロック等）は未送信として UI に残し続け、 ユーザーの手動破棄を待つ。資格はメタデータ面の情報で判定し、 表示層とは別の単純な判定関数にできる。
  • 容量管理: update ログの肥大化にはロード時の compaction で対処 （エントリ数が閾値（目安 500）を超えたら Y.encodeStateAsUpdate の マージ済み 1 エントリに書き戻す）。容量上限は設けずブラウザの quota に任せ、 QuotaExceededError は警告として表示。未送信を失うので自動削除はしない。
  • デフォルト ON + 端末ごとの opt-out: オフライン編集はデフォルトで有効。 設定に「この端末でオフライン編集を使わない」トグルを置く（localStorage ベースの 端末ローカル設定。共有端末で痕跡を残したくない場合向け）。OFF にすると IndexeddbPersistence を付けずオンライン編集のみに戻り、 既存 doc は確認ダイアログで「削除する / 残す」を選ばせる。
  • purge 対象に編集層を含める: 表示層の purge は編集層の y-indexeddb DB も消す（Q2 の未送信ガード通過後）。doc 名は yjs-<userId>-<noteId> 規約 + 表示層 settings 内の doc レジストリで列挙する （indexedDB.databases() は Firefox/Safari 非対応のため使わない）。 purge 墓標の自己修復対象にも編集層を含める。 サーバー側で削除されたノートの doc は、同期済みなら削除・未送信なら 「同期待ち」リストで提示する（Q6 のルールに従う）。
  • 対象外のままの操作: タイトル変更・公開範囲変更など メタデータ操作は REST 経由のためオンライン限定。公開共有ページ （/s/:id・ゲスト閲覧）のオフライン対応は現行どおり対象外。 同一ノートの複数タブ編集は y-websocket の BroadcastChannel 同期が オフラインでも効くため追加実装なしで整合する。
  • 資格判定は stale を許容: 資格は直近のメタデータで判定する。 オフライン中に他端末で共有化されても、再接続時の Yjs マージが正しく 吸収する（owner の編集は常に有効）。検知は「資格を失ったことが判明した タイミング」で sync-then-evict に入ればよい。
  • 未送信の UI 提示は 2 箇所だけ: ①エディタ内の 「未送信の編集あり（オフライン）」バッジ（provider.synced === false、 同期で自動消滅）、②Q2 の purge ガードモーダルの対象一覧。 オンラインなのに sync されない場合（サーバー拒否の可能性）は 「同期待ち」として区別表示する。ホームやノート一覧への常設 インジケーターは設けない。
  • 本文表示ソースの優先順位: ローカル Y.Doc（あれば）→ OPFS スナップショット → ネットワーク。 doc が存在するノートは Y.Doc がローカル最新真実（未送信編集を含む）なので 閲覧表示もそこから行う。doc がなければ OPFS スナップショット。 表示層は資格判定を知らず「doc の有無」だけを見る。 OPFS .md は doc 破棄後・非資格ノート用のフォールバックとして 全ノートで従来どおり書き続ける。
  • 閲覧専用・共有ノート: y-indexeddb に載せない。 オフラインでは従来どおり読み取り専用表示（表示層のスナップショット）。
  • 前提: 一度オンラインで同期したノートのみ編集可 — ローカルで新規 Y.Doc を作ってスナップショット本文を挿入すると、 サーバーと履歴が共有されないため sync 時に本文が二重化する （同じ文字列でも異なる item ID で挿入される）。そのため y-indexeddb に doc がないノートはオフラインでは閲覧のみとし、 「一度オンラインで開くとオフライン編集できます」と案内する。 サーバーから Y.Doc update を seed するエンドポイント （GET /api/notes/:id/yjs-state 案）は将来の拡張として残す。
  • オフライン操作は本文編集のみ: 新規作成・削除・フォルダ移動・ 共有変更・画像添付はオンライン限定（オフライン時は UI を disabled/非表示）。 作成はサーバーが short_id/notes 行を払い出すため仮 ID 機構が必要で、 将来要件として Issue 化（#118）。
  • 未送信編集と purge の衝突を防ぐ: ログアウト・アカウント切替・ 「この端末のキャッシュを削除」の前に、編集層に未送信 update が残っていないか 検査する。残っている場合はモーダルで対象ノートを列挙し 「同期してから実行（オンライン時）/ 編集を破棄して実行 / キャンセル」を選ばせる。 オフライン中のログアウト要求は「オンラインでやり直してください」と案内。 doc は userId 込みでキーイングし、別アカウントへ見せない。

4.4 表示キャッシュの権威モデル — epoch フェンスを維持するか

案 A: 現行の epoch フェンスを維持

  • 読み書き全てが捕捉済み scope epoch を持ち回り、トランザクション内で再検証する。
  • 利点: 通知を逃したタブでも書き込みが確実に止まる（理論上は最強）。
  • 欠点: 中断墓標で永久ロック、タブ間 suspend 伝搬毒、表示と権威の結合、4 系統の世代、約 3,800 行の維持コスト。障害が「正しさ」でなく「可用性」を直撃する。
  • 実態: 「通知が届かない最悪ケース」を防ぐための機構が、通知が届く通常ケースでも毎操作の失敗要因になっている。

案 B: ネットワーク優先 + 拒否台帳 + 自己修復墓標（推奨）

  • データ面（folders / notes / note-lists / OPFS）はフェンスなしの last-write-wins。
  • 権威面は「拒否台帳」と「purge 世代カウンタ」だけを durable に保持し、書き込みトランザクション内でその 2 点だけを検査する縮小版 CAS。
  • 読み取りはフェンスなし。読んだ時点のデータ＋拒否台帳の射影を返す。
  • purge は「墓標 → 削除 → 墓標除去」。墓標を見つけたオープンはロックで生存確認して自己修復。
推奨: 案 B（薄いフェンスつき）

「グローバル epoch を全操作に持ち回る」方式をやめ、書き込み時に自分のトランザクション内で 「対象リソースの拒否世代」と「ユーザーの purge 世代」だけを照合する方式に置き換える。 これにより cross-tab での「古い書き込みが purge 後に復活する」「拒否確定後に古い 200 が保存される」 という本来の安全要件は維持しつつ、読み取り経路から権威検証を完全に取り除ける。 失うものは「読み取り中に他タブで確定した拒否を即座に観測する保証」だが、それは BroadcastChannel 通知＋次回読み取りでカバーでき、現行でも非フェンスなインメモリ通知頼みの 部分があったため実害は小さい。

判断基準: 「fail-closed が必要なのは 表示キャッシュへの書き込み（拒否確定後の 復活防止 CAS と purge 世代照合）だけ。読み取りと拒否台帳への書き込み は best-effort でよい — 台帳書き込みが失敗しても次回オンライン時の再 403/404 で収束する」。 現行設計はこの区別をしていない。

4.6 新しい読み書きフロー

オンライン読み取り（ホーム / ノート共通）

network fetch → snapshot 構築 → display台帳を待たず即表示 ＋ detached save失敗は cacheWarning のみ ＋ project(denials)台帳到着時に再射影。未読込でもブロックしない
  • キャッシュ保存は表示経路から分岐し、失敗しても snapshot は返る。
  • 射影は「保存済み台帳の読み取り」だけで完結し、書き込みハンドルやスコープ捕捉を必要としない。台帳が未読込なら表示を先に出し、到着時に拒否ノートを差し引いて再描画する（§3.3 の許容範囲）。

オフライン読み取り

cache.get → display台帳が読めていれば射影、失敗・未読込でもそのまま表示 or 「オンラインで開いてください」未キャッシュ・墓標・読み取り失敗は全て同じ案内

オフライン表示でも拒否台帳の読み込みを待たない。キャッシュは「保存時点で許可されていた データ」なので、台帳の読み取り失敗や到着遅延で表示を止めない。 台帳が利用可能になれば遅れて再射影し、オンライン復帰時の再検証が最終的な正しさを保証する。

書き込み（縮小版 CAS）

書き込み txn 開始 → 対象リソースの拒否世代 ≦ 読み取り開始時? → purge 世代 == 捕捉時? → put → commit （不一致 → skip。エラーではなく「書かなかった」）

グローバル epoch ではなく「そのリソースに関係する世代」だけを見るため、 無関係なユーザーの変更や別リソースの拒否で書き込みが潰れない。

オフライン編集（編集層 — self 専有ノート）

資格判定effectiveWriteScope === "self" → y-indexeddb から Y.Doc 復元未送信 update 含む → 編集update が IDB に即蓄積 → 再接続時 y-websocket syncYjs が自動マージ → D1 snapshot 射影従来どおり

表示層の読み書きフローとは一切の状態を共有しない。編集可否は資格判定だけで決まり、 「キャッシュ権威が生きているか」は編集層の関心事ではない。

4.7 purge 中断の自己修復

purge 墓標を書く{kind: "user"|"device", startedAt} → データ削除IDB 範囲削除 → OPFS 削除 → 墓標を消す完了
open 時に墓標を発見 → exclusive lock を ifAvailable で試行 → 取れた = 前の purge 死亡 → 削除を完了して墓標除去 or 取れない = 生きた purge 実行中 → 「キャッシュ空」として継続

現在の :purging 墓標は「永久に拒否し続ける」方向にのみ働くが、 新設計では墓標 = 「未完の仕事」へのポインタに変える。 中断しても次のオープンで必ず収束し、ユーザー操作を必要としない。

4.8 タブ間調停の簡素化

なお編集層のタブ間調停は Yjs に委譲できる。同じノートを複数タブで開いた場合も y-indexeddb と BroadcastChannel 経由で Y.Doc が同期されるため、 表示層のための調停機構を編集データへ適用する必要はない。

  • BroadcastChannel は「再読込ヒント」に限定。 {type: "cache-changed", userId} / {type: "purged", userId} / {type: "denied", userId, aliases} を受けたタブは、表示中データを再読み込みするだけ。 自分の suspend フラグを立てない。通知を逃しても durable 側が正。
  • Web Locks は purge / GC / prefetch の 3 箇所だけ。 全キャッシュ操作を包む shared lock の二重構造（global ⊂ user）は廃止し、 破壊的操作だけを exclusive にする。
  • 拒否の伝搬は durable 台帳が担う。 別タブで確定した拒否は、こちらの「書き込み時 CAS」と「次回読み取りの射影」で観測する。 インメモリ世代をタブ間で同期しようとしない。

6移行計画

Phase 番号は設計上の依存関係。実装・リリースの推奨順序は 0 → 1 → 5（編集層）→ 2 → 3 → 4。 Phase 5 は表示層と独立しており後方互換的に追加できるため、 早い段階で「オフライン編集」の価値を届けられる。

0
表示経路の fail-soft 化（既存コードのまま）

home-metadata-reader.ts と cached-drive-reader.ts で、 キャッシュ内部由来の AbortError / scope invalidation を UI へ投げない。 ネットワーク結果が取れていれば常に表示し、キャッシュ失敗は警告のみ。 PR #117 の方針を「再読み込み射影の失敗」「validateHomePublication」にも拡張する。

リスク: 低 既存構造を変えない。ただし根本機構は残るため対症療法。
1
purge 墓標の自己修復（現行 epoch 機構のまま）

openOfflineCache / scope 捕捉時に :purging 墓標や device-clear-state="purging" を見つけたら、対応する exclusive lock を ifAvailable で試行し、取れたら purge を完了させる。 「永久に塞がれた状態」を解消するだけで UX は大きく改善する。

リスク: 中 ロックと purge の対応関係を壊さないよう注意。テストで中断シナリオを注入。
2
DB v5: 拒否台帳と設定ストアへの分割 + epoch 機構の撤去（全消去移行）

metadata を settings（viewer-id / drive-root / purge 世代・墓標 / doc レジストリ）と denials（拒否マーカー＋世代カウンタ）へ分割。 device-epoch / user-epoch / device-clear-state を廃止し、 ユーザー単位の purge 世代カウンタに置き換える。

移行は「全消去して空で継続」。表示キャッシュは読み捨て可能なので upgrade でデータ移行せず全削除＋再フェッチに任せる。拒否台帳も移行しない （キャッシュ本体が消えるので復活対象がなく、拒否は次回の 403/404 で再確立される）。 OPFS も同時にクリア。移行写経コードを持たないこと自体が保守コストの削減。

リスク: 中 既存ユーザーのキャッシュが一度消失し再構築される。失敗時も同じ「空として継続」に縮退。
3
インメモリ realm の撤去と BroadcastChannel 統合

globalSuspended / suspendedUsers / lifetime 系を削除し、 fail-closed は durable 台帳と墓標に一本化。BroadcastChannel を 1 本に統合し、 受信側は「再読み込み」だけを行うように変更。

リスク: 中 既存 offline-*.spec.ts の期待値（invalidatedError）を書き換える必要がある。
4
リーダーの単純化（fetch → project → display）

home-metadata-reader を「ネットワーク取得 → snapshot 構築 → 台帳射影」 の純粋な流れに作り替え、保存は detached に。キャッシュ読み戻しによる射影をやめ、 スコープ捕捉・公開検証・権威 authority の持ち回りを公開 API から除去。

リスク: 中 拒否射影の純粋関数化が前提。段階的に切り替える。
5
編集層の導入（y-indexeddb）— 表示層と並行可能

createYjsSession に IndexeddbPersistence を追加し、 effectiveWriteScope === "self" かつ canWrite コラボレーターのいない ノートのみローカル永続化する。資格喪失（共有化・権限変更）を検知したら ローカル doc を破棄。provider.synced で「未送信の編集」表示もここで入れる。 表示層の再設計（Phase 0-4）とは独立に進められる。

リスク: 中 資格判定と doc 破棄のタイミング設計が要点。サーバー側の変更は不要（DocumentRoom は既に Yjs）。
6
残りの仕上げ — GC 緩和・suspend の durable 化・テスト更新

orphan GC を破損レコード単位でスキップ可能にし、「拒否永続化失敗時の suspend」を durable な「キャッシュ無効」フラグに置き換える（purge 成功または明示クリアで解除）。 全 offline-*.spec.ts を新しい契約（AbortError を投げない、fail-soft 読み取り）に合わせて更新。

リスク: 中 テストの契約変更が大きい。各段階で RED → GREEN を確認。
移行の進め方

Phase 0–1 は現行 v4 DB を壊さずに適用でき、Phase 2 でスキーマを切り替える。 各 Phase は独立してデプロイ可能で、Phase 2 以降も「失敗したらキャッシュを捨てて オンライン表示に縮退」する安全網を残す。どの段階で止まっても、 現行より悪い状態にはならないことを各 Phase の完了条件にする。
